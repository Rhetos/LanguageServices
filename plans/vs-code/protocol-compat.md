# Protocol compatibility: server behaviors to verify or change for VS Code

Back to [README.md](README.md). Items marked **Prereq** are also listed in Part A of [../prerequisites-and-improvements.md](../prerequisites-and-improvements.md).

Column "Today" describes the current server code on `master` (6.1.0-dev).

| # | Area | Today | VS Code behavior | Action |
| --- | --- | --- | --- | --- |
| 1 | Document URIs | Handlers call `request.TextDocument.Uri.ToUri()` and the workspace is keyed by `System.Uri`. `PublishDiagnosticsRunner` converts `System.Uri` back to `DocumentUri` implicitly. Branch `path-case` (2022, unmerged) targeted casing differences with VS; the A3 analysis could not reproduce one | VS Code sends `file:///c%3A/Users/x/Module.rhe` (lower-case drive letter, percent-encoded colon). Diagnostics must come back with an equivalent URI or they are not matched to the editor; `System.Uri` round-trips to `file:///c:/Users/...`, which VS Code normalizes in most cases but not guaranteed for all code paths (e.g. `untitled:`) | **Prereq A3** (implemented): key the workspace by the URI string the server receives and publish with that same URI (canonical form `file:///c:/...`, because OmniSharp 0.19.9 cannot echo the client's exact string; VS Code treats both as one resource); use `LocalPath` only for file-system work. Add integration tests with both URI spellings and with spaces/non-ASCII in paths |
| 2 | Language id | `TextDocumentHandler.GetTextDocumentAttributes` returns language `"csharp"` while all `DocumentSelector`s are `ForLanguage("rhetos-dsl")`. It works in VS because OmniSharp falls back to the only registered handler | VS Code sends `languageId: "rhetos-dsl"` in `didOpen` (from `contributes.languages`) | **Prereq A4**: return `"rhetos-dsl"` from `GetTextDocumentAttributes`; keep a single constant for the id |
| 3 | Capability registration | `DisableDynamicCapabilityRegistration` forces static registration because VS 2022 misbehaves | VS Code supports dynamic registration, but static registration is fully supported too | Keep as is. Verify in the `initialize` response that `hoverProvider`, `completionProvider`, `signatureHelpProvider` and `textDocumentSync` are present (OmniSharp emits them from the handlers' registration options) |
| 4 | Text sync | Full sync; `OnInitialized` forces `TextDocumentSync.Kind = Full` and `Change = Full`; `DidChange` reads `ContentChanges.First().Text` | VS Code honors full sync; sends `didSave` with text because `Save.IncludeText = true` | Works. Later improvement: incremental sync (Part B) |
| 5 | Hover content | `new MarkedStringsOrMarkupContent(string)` -> a plain `MarkedString`. The text is built with `\n` line breaks and lines starting with `* ` (`ConceptQueries.CreateRhetosSignature`) | VS Code renders `MarkedString` as **Markdown**: single newlines collapse into one paragraph, `* ` becomes a bullet list, `<...>` segments may be stripped as HTML, `_` and `*` inside identifiers italicize | **Prereq A4**: build a `MarkupContent` deliberately. Recommended: Markdown with the signature in a fenced block (```` ```rhetos ```` or ```` ```text ````), documentation as paragraphs separated by blank lines, and Markdown-escaped identifiers. Use the client's `textDocument.hover.contentFormat` to fall back to `PlainText` when Markdown is not supported |
| 6 | Empty hover | Returns a `Hover` with empty `MarkupContent` because VS 2019 cannot handle `null` | VS Code expects `null` for "no hover"; an empty hover may render an empty box | **Prereq A4**: always return `null`. VS 2019 support is dropped (prerequisite A0), and VS 2022 handles `null` correctly |
| 7 | Completion items | `Detail` holds the full multi-line description; `Documentation` is not set; `Kind = Keyword` | VS Code shows `Detail` on one line next to the label and `Documentation` in the details pane. Multi-line `Detail` is truncated | **Prereq A4**: `Detail` = short signature, `Documentation` = `MarkupContent` with the full text (same builder as hover). Consider `SortText`/`FilterText` for case-insensitive keyword matching (`Keywords` dictionary is case-insensitive) |
| 8 | Completion triggers | `TriggerCharacters = "."`, `AllCommitCharacters` empty | Same semantics | Works. Verify that typing a keyword prefix at line start triggers completion through VS Code's 24x7 word-based trigger (it does for `rhetos-dsl` once the language is registered) |
| 9 | Signature help | `ActiveSignature`/`ActiveParameter` default to `100` when the analysis returns null; triggers `"."` and `" "` | VS Code clamps out-of-range `activeSignature` to 0 but may highlight no parameter or the wrong one; space as a trigger pops signature help after every space, including inside strings | **Prereq A4**: send `0` or omit the field instead of `100`. Keep space trigger (same as VS) but verify UX; optionally add `RetriggerCharacters` |
| 10 | Diagnostics | Push model: `PublishDiagnosticsRunner` polls the workspace every 300 ms; `Code` is a string; severity Error/Warning; closed documents get an empty list | Standard | Works. Severity `Information`/`Hint` could be used for the "waiting for initialization" message. Later: event-driven publishing (Part B5) |
| 11 | Server logging to client | `AddLanguageProtocolLogging` sends `window/logMessage` (Information+ for `Rhetos.LanguageServices.*`, Warning+ for others). On initialize the server logs its own path and the log file path | Messages appear in the extension's Output channel. VS Code also shows `window/showMessage` as toasts; the server does not use it | Works. Add `--log-level` command-line option (Prereq A5) so `rhetos.languageServer.logLevel` can control the file log; keep stdout strictly for JSON-RPC (NLog `logconsole` target must never be enabled in rules) |
| 12 | Process lifecycle | `OrphanedProcessMonitor` watches `InitializeParams.ProcessId`, exits with code 2 if the host dies; `shutdown`/`exit` stop the loops | VS Code sends `processId`, then `shutdown` + `exit` on deactivate; it force-kills after a few seconds | Works. `Environment.Exit(2)` on orphan is fine. Verify no zombie `dotnet` processes after "Developer: Reload Window" |
| 13 | Position encoding | Server works with UTF-16 code units (`LineChr`), CRLF and LF handled by `TextDocument` | LSP default is UTF-16; VS Code negotiates `positionEncodings` (3.17) but defaults to UTF-16 | Works. Do not advertise `utf-8` |
| 14 | Root detection | Per document: directive, `rhetos-language-services.settings.json`, parent folder with `obj/Rhetos/DslSyntax.json`. `rootUri`/`workspaceFolders` are ignored | VS Code may open `.rhe` files outside the workspace, in multi-root workspaces or as `untitled:` | Works for `file:`. `untitled:` documents have no `LocalPath`; the resolver must not throw (today `Path.GetDirectoryName` on an `untitled:` URI would). Either exclude `untitled` from the document selector or guard the resolver (Prereq A3) |
| 15 | Messages mentioning Visual Studio | `RhetosDocument.BlockedAnalysisResult`: "Restart Visual Studio if you want to use a different Rhetos app." | Misleading in VS Code | **Prereq A4**: "Restart the language server (or the IDE)". The workspace already switches context when all open documents move to another root path, so the message is partly stale anyway |
| 16 | Configuration requests | No `workspace/configuration` use; OmniSharp's `DidChangeConfigurationProvider` warnings are filtered out | VS Code sends `workspace/didChangeConfiguration` only if the client registers `synchronize.configurationSection`; the plan does not | Nothing to do for v1 |
| 17 | File watching | `RhetosProjectMonitor` polls `DslSyntax.json` timestamp every 1 s | VS Code can send `workspace/didChangeWatchedFiles` if the client registers a watcher | Optional later: handle the notification to refresh immediately and reduce polling |
| 18 | Cancellation | Handlers ignore `CancellationToken`; analysis is synchronous under a global lock | VS Code cancels completion/hover aggressively while typing; ignored cancellations just waste CPU | Later (Part B6): honor the token before starting analysis |
| 19 | Unknown document | `RhetosWorkspace.GetRhetosDocument` throws; only the hover handler catches it. VS 2019 could send hover before `didOpen` | VS Code never sends requests before `didOpen`, but a race after `didClose` is possible | Later (Part B6): completion and signature help should return `null` instead of surfacing an exception |
| 20 | Workspace-level errors | Initialization errors are attached to every document as a diagnostic | Same | Works. Optionally also `window/showMessage` once per initialization failure so users see it even without an open document |
| 21 | Working directory | NLog.config is loaded relative to the process base directory (assembly location), not cwd | VS Code starts the process with cwd = workspace folder unless `options.cwd` is set | Works either way; set `cwd` to the server folder defensively |
| 22 | Log file location | `NLog.config`: `${specialfolder:folder=CommonApplicationData}/Rhetos.LanguageServices/...` = `C:\ProgramData` | Not writable on many systems; on Linux it maps to `/usr/share` | **Prereq A5**: `LocalApplicationData` (or `${tempdir}`), overridable with `--log-file` |

## Test matrix after the changes

Run these with the VS Code client against the server and record the result in [testing-and-debugging.md](testing-and-debugging.md):

1. Open a `.rhe` inside a built Rhetos app: diagnostics appear within ~1 s, hover shows Markdown correctly formatted, completion shows keywords with documentation pane, signature help highlights the active parameter.
2. Same file opened via a workspace whose folder path contains a space and a non-ASCII character.
3. `.rhe` outside any Rhetos app: single warning diagnostic with the explanation text.
4. Two `.rhe` files from two different Rhetos apps open at once: second file shows the "different Rhetos app" warning; close the first file and the context switches within ~1 s.
5. Delete `obj/Rhetos` while the file is open: diagnostics switch to the "not built" warning; rebuild: diagnostics recover.
6. "Developer: Reload Window" and closing VS Code: no leftover `dotnet` processes.
7. Kill the server process manually: `vscode-languageclient` restarts it up to 5 times; the "Restart Language Server" command works afterwards.
